## 韩国飞书机器人修复（已完成 ✅）

### 问题
韩国飞书机器人回复"无输出" — MiniMax thinking 块触发 CCR response transformer 报错

### 根因
MiniMax 返回 `type: "thinking"` content blocks，CCR 的 `convertOpenAIResponseToAnthropic` 不识别这个类型，直接报错退出

### 修复方案（已验证 ✅）
**在 Claude Code 和 MiniMax 之间加 proxy 层（port 3457）**
- `thinking: {type:'disabled'}` 让 MiniMax 不生成 thinking 内容
- `stream: false` 强制完整 JSON 响应（非流式）
- 过滤响应中的 `thinking` 块和 `base_resp` 字段
- 延迟从 9 秒降至 4 秒

**最终架构**：
```
飞书 → Claude Code → proxy (:3457) → MiniMax API
                     ↑ 强制 stream:false
                     ↑ 过滤 thinking + base_resp
```

### 关键文件
- proxy 脚本：`/home/ccuser/minimax-proxy.mjs`
- 重启命令：`systemctl restart feishu-cc`

## kimi/k2.5 模式（无法使用 ❌）

### 结论
**`/model kimi` 在韩国飞书暂时无法使用**

### 原因
雪子用的是 OpenClaw 的 `nvidia-k2.5` provider（NVIDIA API key），但测试发现：
- NVIDIA API key 只能调用 NVIDIA 托管模型（`nvidia/*`）
- 调用第三方模型如 `moonshotai/kimi-k2.5` 返回 **404 Function not found**
- CCR 的 response transformer 无法处理 thinking 块（插件方案无效）

### 验证命令
```bash
# NVIDIA API 连通性（韩国服务器上测试）
curl -s -X POST https://integrate.api.nvidia.com/v1/chat/completions \
  -H "Authorization: Bearer $NVIDIA_API_KEY" \
  -d '{"model":"moonshotai/kimi-k2.5","messages":[{"role":"user","content":"hi"}]}'
# 返回 404 → key 没有 kimi 权限
```

### 现状
- NVIDIA API 从韩国能连通（延迟 ~7ms）
- 但 key 对 kimi-k2.5 无权限
- CCR transformer 修不了（thinking 块触发 CCR 内部报错，plugin 无法拦截）
- 唯一的稳定方案是 minimax 模式（走 proxy）

## 今日教训
1. **nvidia API key 不包含第三方模型** — 以为有 kimi 访问权限，实际没有
2. **修 CCR transformer 要动源码** — 插件机制在 CCR 内部处理之后，无法拦截 thinking 块
3. **SSH 曾经断过** — Korean server sshd 无响应，后来恢复了
