## 四条核心原则

### 1. 先读再评，不跳步

**Codex 做法：**
- 遇到问题 → 先把相关脚本全读一遍 → 再判断
- 用 `rg`/`grep` 搜引用链，顺藤摸瓜找断点
- 找到关键差异点后再下结论

**我之前的问题：**
- 看到 DeepSeek 报错 → 直接说"方案B最稳"
- 没验证快照机制就直接下结论
- 被 Codex 现场抓包："你先把 session-snapshot.py 读完再说话"

**改进：**
- 遇到不熟悉的机制 → 先读相关代码 → 再发表意见
- 引用数据时标注来源文件

---

### 2. 聚焦核心，不跑题

**Codex 做法：**
- 问题本来是"DeepSeek 兼容性"
- 收窄到两个子问题：①快照内容 ②恢复入口
- 不展开讨论别的模型、别的方案

**我之前的问题：**
- 聊方案时容易发散，从方案A聊到方案C又聊到独立会话
- 用户问一个问题，我绕回来答另一个

**改进：**
- 开口前先想：用户核心问题是什么？
- 回答完问自己：有没有答非所问？

---

### 3. 用证据diss，不空洞

**Codex 做法：**
- 不是"质量一般"这种模糊评价
- 直接指出：`from_memory` 里混进了一条无意义的表格行
- 证据：`["合计 | | ~675MB+ |"]` 这类垃圾数据

**我之前的问题：**
- 喜欢说"我觉得不太好"、"质量一般"
- 没有具体指出哪里不好、证据是什么

**改进：**
- diss 别人之前先问自己：我的证据是什么？
- 给评价必须带具体例子

---

### 4. 给路线，不只抛问题

**Codex 做法：**
- 发现快照质量问题 → 顺手提了两个优化方向
- 实现"切到 DeepSeek 自动新会话"
- 顺手修 session-snapshot.py 的任务提取

**我之前的问题：**
- 只说"这个有问题"，不说"建议怎么改"
- 把问题抛给用户让他们自己决定

**改进：**
- 发现问题后立刻想：你能提供什么解决方案？
- 给出 A/B 两条路线，让用户选

## 本次案例复盘

### 事件
Codex 帮雪子分析 DeepSeek 跨模型切换 400 报错问题

### Codex 的判断链路
```
1. 读 session-snapshot.py 源码
2. 读 auto-save-session.sh
3. 搜快照相关引用
4. 确认快照存的是摘要，不是原始消息
5. 判断这让方案A更稳
6. 指出快照质量问题（from_memory 垃圾数据）
7. 给出路线建议
```

### 我的判断链路
```
1. 说"方案B最稳"（没读代码）
2. 说"方案C更务实"（继续空谈）
3. 说"方案A最合适"（被雪子纠正"我卡了喊你个der"）
4. 说"snapshot 只有10分钟自动保存"（没看 crontab）
5. 被 Codex 现场打脸
```

### 差距总结
| 维度 | Codex | 我 |
|------|-------|-----|
| 读代码 | ✅ 全读完再判断 | ❌ 先下结论后补读 |
| 聚焦核心 | ✅ 收窄到两个子问题 | ❌ 方案间跳来跳去 |
| 用证据 | ✅ 精确到垃圾数据行 | ❌ "质量一般" |
| 给路线 | ✅ 两个优化方向 | ❌ 只抛问题 |

4. **收尾前**：我能提供什么路线建议？
