## 一、核心变化：去掉网页版

### 1.1 变化对比

| 项目 | 旧架构（网页版） | 新架构（独立客户端） |
|------|----------------|---------------------|
| Windows | Electron内嵌网页 | **独立窗口，自带UI** |
| Mac | Electron内嵌网页 | **独立窗口，自带UI** |
| Android | 无 | **React Native独立App** |
| iOS | 无 | **React Native独立App** |
| Web | 有（已砍掉） | ❌ 不再做 |
| 后端API | 完整实现 | **保持不变** |

### 1.2 设计原则
- 客户端不依赖任何外部网页/URL
- 所有UI完全在客户端本地渲染
- 后端API零改动，客户端按需调用
- 离线优先，数据本地优先存储

### 3.3 主进程职责（完全自包含）

**窗口管理：**
- 创建主窗口（无标题栏或标准标题栏，不使用任何外部URL）
- 创建系统托盘（后台运行）
- 创建快速便签窗口（全局快捷键呼出）
- 窗口间通信

**本地数据存储（SQLite）：**
- 笔记内容（本地优先，联网后同步）
- 笔记本/标签元数据
- 同步状态队列
- 用户设置/偏好

**同步引擎：**
- 网络状态检测（每10秒）
- 变更队列管理（本地 → 服务端）
- 拉取最新数据（服务端 → 本地）
- 冲突检测与处理（Last-Write-Wins）
- 同步状态上报给渲染进程

**系统集成：**
- 全局快捷键（全局capture）
- 系统通知
- 自动更新检测与安装
- 文件拖拽处理

### 3.4 渲染进程职责（完全自包含UI）

- 所有UI组件本地渲染（React组件）
- 编辑器：Milkdown（Markdown）、TipTap（富文本）
- 本地搜索（通过IPC调用主进程查询SQLite）
- 远程API调用（笔记搜索、AI RAG等）
- 离线状态提示
- 同步状态展示

### 3.5 修复现有打包配置

当前 `electron-builder` 配置问题排查清单：

### 4.4 移动端离线策略

移动端 **不内置SQLite**，采用更简单的方案：

```
读操作：
  1. 先读 AsyncStorage 缓存
  2. 同时请求后端API（后台）
  3. 返回最新数据后更新缓存

写操作：
  1. 先写入 AsyncStorage 缓存（标记pending）
  2. 立即提交到后端API
  3. 成功 → 更新缓存状态
  4. 失败 → 保留pending，网络恢复后重试

冲突处理：
  移动端统一使用 Last-Write-Wins
  由桌面端（主设备）负责权威冲突解决
```

## 五、离线同步设计

### 5.1 同步架构总览

```
本地存储 ──→ 变更队列 ──→ 同步服务 ──→ 后端API
                ↑
                │ 冲突检测
         ┌──────┴──────┐
         │  Last-Write │
         │    -Wins    │
         └─────────────┘
```

### 5.2 数据模型（SQLite schema）

```sql
-- 笔记表（本地）
CREATE TABLE notes (
  id TEXT PRIMARY KEY,           -- UUID
  title TEXT,
  content TEXT,                  -- Markdown内容
  notebook_id TEXT,
  tags TEXT,                     -- JSON数组
  created_at INTEGER,           -- Unix timestamp
  updated_at INTEGER,            -- Unix timestamp (用于LWW)
  synced_at INTEGER,            -- 最后同步时间
  sync_status TEXT DEFAULT 'pending',  -- pending/synced/conflict
  is_deleted INTEGER DEFAULT 0,  -- 软删除
  client_updated_at INTEGER,    -- 客户端最后修改时间
  server_updated_at INTEGER     -- 服务端最后修改时间（用于冲突检测）
);

-- 笔记本表（本地）
CREATE TABLE notebooks (
  id TEXT PRIMARY KEY,
  name TEXT,
  parent_id TEXT,
  color TEXT,
  created_at INTEGER,
  updated_at INTEGER,
  synced_at INTEGER,
  sync_status TEXT DEFAULT 'pending',
  is_deleted INTEGER DEFAULT 0,
  sort_order INTEGER
);

-- 标签表（本地）
CREATE TABLE tags (
  id TEXT PRIMARY KEY,
  name TEXT,
  color TEXT,
  created_at INTEGER,
  sync_status TEXT DEFAULT 'pending',
  is_deleted INTEGER DEFAULT 0
);

-- 同步队列（待推送变更）
CREATE TABLE sync_queue (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  table_name TEXT,
  record_id TEXT,
  operation TEXT,                -- INSERT/UPDATE/DELETE
  payload TEXT,                  -- JSON数据
  created_at INTEGER,
  retry_count INTEGER DEFAULT 0,
  last_error TEXT
);

-- 同步元数据
CREATE TABLE sync_meta (
  key TEXT PRIMARY KEY,
  value TEXT
);
```

### 5.3 同步流程

#### 5.3.1 拉取同步（Pull）
```
1. 检测网络可用
2. 从服务端获取「最后同步时间」后的变更记录
3. 遍历每条记录：
   a. 本地无此记录 → INSERT
   b. 本地存在且 server_updated_at 相等 → 跳过（已同步）
   c. 本地存在且 server_updated_at 更新 → 冲突 → Last-Write-Wins
4. 更新本地 synced_at
5. 通知渲染进程刷新UI
```

#### 5.3.2 推送同步（Push）
```
1. 从 sync_queue 读取 pending 记录（按created_at顺序）
2. 批量提交到服务端
3. 成功 → 删除队列记录，更新本地 synced_at
4. 失败 → retry_count++，记录错误
5. 超过3次失败 → 暂停，通知用户
```

#### 5.3.3 冲突处理策略（Last-Write-Wins）
```
规则：
  - 比较 client_updated_at 和 server_updated_at
  - 时间戳大的为胜者
  - 败者的内容保存到 conflict_history 表（保留7天）

冲突解决优先级：
  1. 手动编辑过的笔记 → 以本地为准
  2. 无手动编辑 → 以服务端为准
  3. 用户可在桌面端「冲突管理」界面手动选择保留版本
```

### 5.4 同步时机

| 场景 | 触发条件 |
|------|---------|
| 启动同步 | App启动时 + 登录后 |
| 退出同步 | App关闭/最小化到托盘 |
| 定时同步 | 每30秒自动检查（仅在联网状态） |
| 网络恢复 | 检测到网络从离线变为在线 |
| 手动同步 | 用户主动点击「同步」按钮 |
| 数据变更后 | 本地写操作完成后立即入队，网络可用时立即推送 |

### 5.5 移动端同步（简化版）

移动端不内置完整同步引擎，使用更简单的策略：

```
变更时：
  1. 写入 AsyncStorage（标记pending）
  2. 同时POST到后端API
  3. API返回成功 → 更新AsyncStorage状态
  4. API失败 → 保留pending，下次打开App重试

读取时：
  1. 显示AsyncStorage缓存
  2. 后台GET后端API
  3. 收到新数据 → 合并到AsyncStorage + 更新UI
```

## 七、关键设计决策

### 7.1 桌面端 vs 移动端职责划分

| 决策 | 选择 | 理由 |
|------|------|------|
| 移动端是否内置SQLite | **否** | 移动端离线写入频率低，AsyncStorage足够 |
| 移动端同步权威 | **桌面端为主** | 桌面端为完整设备，移动端为便捷访问 |
| 冲突解决 | **Last-Write-Wins** | 最简单有效，用户无感知 |
| AI RAG | **统一走后端API** | 客户端不内置AI能力，保持轻量 |

### 7.2 后端API无需改动

所有现有后端API保持不变：
- 笔记CRUD：`/api/notes/*`
- 笔记本：`/api/notebooks/*`
- 标签：`/api/tags/*`
- 搜索：`/api/search/*`
- AI RAG：`/api/ai/*`
- 日程：`/api/schedules/*`
- 文件：`/api/files/*`
- 同步：`/api/sync/*`

### 7.3 客户端认证

统一使用JWT Token：
- 桌面端：首次登录后Token存SQLite
- 移动端：Token存AsyncStorage（加密）
- Token刷新机制：后端API统一处理

## 八、风险与应对

| 风险 | 等级 | 应对措施 |
|------|------|---------|
| Electron打包native模块失败 | 中 | 使用 `@electron/rebuild`，Phase 1优先解决 |
| 移动端离线写入冲突 | 中 | Last-Write-Wins + 冲突历史保留 |
| 同步队列堆积（长期离线） | 低 | 队列上限1000条，超出提示用户 |
| 后端API性能（大量同步请求） | 低 | 批量API + 限流，桌面端可配置同步间隔 |
| better-sqlite3 版本兼容 | 低 | Node 20 LTS + Electron 33，固定版本 |
